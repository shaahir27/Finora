# Decision Log — Smart School FinTech Platform

## Purpose

A chronological record of every significant design decision, the reasoning behind it, and — where applicable — decisions that were made and later reversed or revised. An AI coding agent encountering an apparent inconsistency between documents should consult this log first: it is very likely a documented, deliberate revision, not a contradiction to silently resolve on its own.

## Scope

Decisions from Phase 1 (MVP scoping) through Phase 7 (documentation). Does not restate the content of each decision in full — points to the authoritative document for current-state detail.

## Phase 1 — MVP Design

- Feature set tiered into Must/Should/Nice/Future/Out-of-Scope, cut against the research's own named judging criteria and failure-mode risks (§13.1–13.4, §14.1). See `product_requirements.md` for current tiering.
- ML-based defaulter risk scoring and live KYC payment integration explicitly declined, with reasons stated rather than silently dropped (ML conflicts with the research's own rule-based-sufficiency finding at §10.1; live KYC is a named time-sink risk at §14.1).

## Phase 2 — Product Design

- **Parent portal scope reconsidered mid-phase.** Initially filed under "Source B's inference," corrected on review: §2.5 lists parent-facing UI as a stated Key Feature, not an inference, and §4.3's competitor matrix shows parent portals as near-universal table stakes. Parent scope moved from "Future Scope, design-ready only" to **Should Have**, deliberately scoped small (FR-18–21: login, view dues, pay via UPI sandbox, view history/receipts) to avoid competing with the reconciliation engine for build time. ## Phase 3 — System Design

- Full schema, architecture, API contracts, RLS-based authorization established.
- **Cheque clearance logic — decided, then reversed.** Original decision: treat cheques identically to cash (post immediately, no distinct state), justified by hackathon time constraints and the absence of an explicit research requirement for bounce-tracking. **Reversed** once the product owner clarified the entire product (not just a hackathon demo) is being built — cash and cheque are not equivalent risk profiles in reality, so `cheque_pending` was added as a distinct `reconciliation_status`, with `markChequeCleared`/`markChequeBounced` actions and a mandatory defaulter-score recompute on bounce. Current state is authoritative in `database_design.md`, `financial_engine.md`, and `user_flows.md`.
- Notification flow, offline payment handling, integration failure modes, deployment strategy, and scalability considerations added to close gaps against the product owner's own original Phase 3 checklist, which the first pass had left incomplete.

## Phase 4 — UI/UX Design

- Initial approach favored wireframing only the two screens tied directly to scored judging criteria (dashboard, parent pay flow), reasoning that hackathon judging time was the binding constraint. **Reversed** once the product owner clarified the full product is being built by AI agents, not just demoed — every screen now has a written requirement in `ui_ux_specification.md`, though only two were rendered as visual mockups (the rest are text specifications, which is what an agent needs, not necessarily a rendered image).
- **Partial payment**: added as a requirement, with the ambiguity between "same due date, no extension" versus "separate grace period from the partial-payment date" explicitly raised. Product owner did not correct the assumption; **"same due date, no extension" was adopted as the operative rule** — this is the lower-risk interpretation for a fee-collection system and is now reflected throughout `business_rules.md`, `financial_engine.md`, and the Parent Pay screen spec.
- **Multi-child parent view**: confirmed by the product owner as a same-school-or-different-school-agnostic selector — any parent with more than one `PARENT_LINK` sees a selector; a parent with exactly one sees no selector element at all, not merely a hidden one.
- **Color palette explicitly deferred** to the product owner at their request, at this point in the process — `design_system.md` at this Phase 4 stage specified semantic tokens only, no hex values. **Superseded**: the palette was subsequently finalized (three fully-mocked, WCAG-verified dark-theme candidates reviewed; Option A "Forest Ledger" selected) and `design_system.md` now contains final, locked hex values — see Phase 8 below. This Phase 4 entry is preserved as a historical record of the original deferral, not as current state.

## Phase 5 — Business Intelligence

- Risk-scoring weights and reminder-tier thresholds were proposed as defaults and formally **approved by the product owner** rather than independently decided: `risk_score = (days_overdue × 2) + (broken_promise_count × 15) + (remaining_balance_ratio × 30)`, thresholds 60/30 for high/medium; reminder tiers at 1/7/14 days overdue. Both stored as tunable constants, not inlined logic, by design.
- Late fees and penalties decided as manual, reason-tagged entries rather than automatic accrual engines — no research citation demanded automatic accrual, and the added complexity (caps, compounding, rounding) had no specified rules to build against.
- Post-full-payment waiver/refund workflow explicitly deferred as out of scope — flagged as a genuinely different workflow (money already collected vs. balance adjustment) rather than silently folded into standard waiver handling.

## Phase 6 — Design Review

Four issues found and fixed in this pass, all now reflected as current state in the relevant documents (not superseded elsewhere):

1. **Webhook idempotency** — missing duplicate-delivery protection on the Razorpay webhook path; fixed by requiring a `ref_number` existence check before any UPI transaction insert.
2. **AI narration on the payment-critical path** — `narrateAnomaly` was originally specified as part of the same synchronous step as `detectAnomaly`, contradicting the project's own rule that AI failures must never affect payment-critical timing. Fixed by moving all narration calls to run asynchronously, after the triggering write's response has already returned.
3. **Stale `getMyChildrenDues` contract** — specified before partial payment existed; updated to return the full paid/remaining breakdown.
4. **Waiver-triggered recompute gap** — `applyWaiver` did not originally trigger an immediate `computeDefaulterScore` recompute, meaning a resolved issue could still show a stale "high risk" badge. Fixed by making the recompute part of the waiver-application workflow itself, not deferred to the next scheduled job.

**GST research conducted** at the product owner's request, since the original research document did not address it. Findings (cross-checked across the GST Council's own guidance and multiple independent tax-advisory sources): core K-12 tuition/exam fees are generally GST-exempt; non-academic goods are generally taxable; **sources genuinely disagree on whether for-profit-operated schools lose the tuition exemption** — this ambiguity was not resolved and is explicitly flagged in `business_rules.md` as outside the system's ability to determine automatically. Resulting decision: GST treatment is configured per fee type by the admin, never inferred by the system.

## Phase 7 (continued) — GST-Inclusive Convention Resolved

Following dedicated research into Indian GST/consumer-pricing law (undertaken because the product owner had no prior context on this and asked for a researched recommendation, not a guess), the GST-inclusive-vs-exclusive open item was resolved: **GST-inclusive** is the decided convention for all taxable fee types. Reasoning: a parent paying school fees is an end consumer, not a GST-registered business claiming input tax credit — that places the relationship squarely in the B2C case, where Indian consumer-protection precedent (Legal Metrology's MRP-inclusive rule; *Aero Club (Woodland) vs. Rakesh Sharma*, NCDRC) treats adding tax on top of an already-quoted consumer price as an unfair trade practice. B2B exclusive-pricing convention, which several general GST explainer sources default to, does not apply here. This is now reflected as current state in `business_rules.md` §8, `financial_engine.md` §5, and the Fee Engine labeling requirement in `ui_ux_specification.md` — not merely noted as a decision in this log.

## Phase 8 — Design Audit Remediation

A structured design audit (external review, covering all 13 companion documents) surfaced two real cross-document contradictions, both root-caused to the same underlying process gap: a decision was made and recorded in this log, but the affected document's body text was never actually edited to match, so the log and the document disagreed with each other. Both are corrected as of this phase:

1. **GST-inclusive convention (`financial_engine.md` §5).** The convention was correctly decided in Phase 7 (continued) and correctly reflected in `business_rules.md` §GST Logic, but `financial_engine.md` §5 still contained the pre-decision exclusive-pricing formula and "not yet decided" language, plus a standalone "Open Item Requiring Confirmation" section repeating the stale claim. Both are removed; §5 now states the inclusive formula only, with an explicit note that no exclusive code path should ever be implemented.
2. **Color palette finality (`README.md`, `implementation_plan.md` Session 3, this log's own Phase 4 entry and Open Items list).** `design_system.md` had, in fact, been finalized (Option A, "Forest Ledger," confirmed final by the product owner) — but the palette's Phase 4 "deferred" status was never updated in the three other documents that referenced it, so they continued to describe it as an open item after it had already been closed. All three are corrected to state the palette is final.

**Governing policy adopted from this phase forward**: no decision may be marked resolved in this log until the specific document(s) it affects have been re-read and confirmed (not assumed) to reflect the resolution in their body text — a log entry describing a decision is not itself evidence the decision was applied. Future contributors: if you close an open item here, grep the other 13 documents for references to it before closing this entry.

**Additional accessibility correction made during this same pass**: `--color-risk-medium` ("Copper") was re-measured and found to pass WCAG AA (4.5:1) only for large/bold text at its original value (`#B87333`, 3.31:1 against Cream) — the badge specification elsewhere does not guarantee large-scale text, so this was a genuine (if narrow) accessibility risk, not merely a margin worth spot-checking as originally framed. The token was darkened to `#9C5E22` (4.54:1 against Cream), which passes AA for normal-size text while preserving the same copper/burnt-amber hue and semantic role. This is a contrast correction within the already-final palette, not a reopening of the palette decision — all six other source colors are unchanged.

## Phase 9 — PWA, Push Notifications, Weekly Digest, AI Copilot

Four additions made in direct response to a scoping conversation, not a defect fix like Phase 8 — this phase's record is "why we chose to build this and what boundary it's held to," not "what was broken."

**1. Installable PWA.** The original scope was a responsive web app; installability was out of scope by omission. Added because it's cheap (Next.js has native support — manifest + service worker, no new framework) relative to its payoff for a hackathon whose own brief asks for "impactful web solutions." Offline behavior is deliberately minimal (cached static assets + a "last synced at" banner over stale data) rather than full offline-first sync — full offline caching of ledger data would work against the product's own zero-lag claim, so the feature was scoped to stop short of contradicting the thing it's supposed to support.

**2. Web Push notifications.** Distinguished explicitly from the existing, deliberately-simulated WhatsApp/SMS reminder system (Governing Principle 3) — see `business_rules.md` Push Notification Strategy for the full reasoning. This is real, not simulated, because it costs nothing (self-generated VAPID keys, no third-party provider) and directly demonstrates the product's core reconciliation claim to a live audience better than a silently-updating dashboard number does. Scoped narrowly on purpose: admin gets operational alerts (payment posted, cheque bounced, anomaly flagged), parent gets payment confirmation only — explicitly not a second reminder channel, to avoid quietly undermining the deliberateness of the existing simulated-reminder boundary.

**3. Weekly AI digest.** Reuses existing rule-computed aggregates (collection trends, cheque aging, risk movement) narrated by Gemini — no new computation logic, only a new narration surface over numbers the rule engine already produces elsewhere. Chosen specifically because it's a second, genuinely distinct AI use case (summarization over time, vs. the existing per-event narration features) rather than a sixth near-duplicate of "Gemini explains a number," which external hackathon-judging commentary specifically named as something judges are fatigued by seeing repeated within one project.

**4. AI Copilot (Admin + Parent).** The most architecturally significant of the four additions, added specifically to make the AI-powered nature of the product *visible* to end users — the original five AI features are real but easy for a user (or a judge clicking through quickly) to miss, since none of them has a persistent, obviously-AI surface. The design decision that matters most here: **the Copilot is built as a thin conversational layer over the existing, already-RLS-scoped server action set, via Gemini function-calling against a fixed per-role whitelist — never given raw database access, never able to call a write action, for either role, under any framing.** This was chosen over the alternative (a more capable copilot with broader tool access) specifically because a broader-access copilot would have reopened exactly the RLS-based tenant-isolation guarantee `security.md` spends most of its length establishing — for a demo differentiator, that trade was judged not worth it. See `system_architecture.md` AI Copilot Architecture and `security.md` AI Copilot for the full guardrail record, and `testing_strategy.md` Sessions 4/5 for the whitelist-assertion tests this decision requires to actually hold over time, not just at first implementation.

**Process note**: all four additions were cross-referenced against every document they touch before this entry was written (per the Phase 8 governing policy above) — `product_requirements.md`, `business_rules.md`, `system_architecture.md`, `database_design.md`, `api_specification.md`, `security.md`, `ui_ux_specification.md`, `design_system.md`, `implementation_plan.md`, and `testing_strategy.md` were all updated in this same pass, not left for a future sync.

## Phase 10 — Offline Payment Entry (Official Brief Requirement)

Distinct from every prior phase in one important way: this is the first addition sourced from the actual official challenge brief text, not research inference (Phases 1–7) or design judgment (Phases 8–9). The brief's Challenge section states the core objective as designing systems "supporting multiple payment methods **and offline workflows**" — a direct requirement, which is why this is filed as M-7 (Must Have) in `product_requirements.md` rather than at the S/N tier most Phase 9 additions received.

**The design tension that had to be resolved, not avoided**: this project's central pitch is zero-lag, always-current reconciliation. An offline-entered payment is, by construction, un-reconciled for however long the device stays offline — a direct tension with that pitch if handled carelessly. The resolution wasn't to minimize the tension by scoping the feature narrowly into irrelevance (which would technically satisfy the brief while defeating its purpose) or to paper over it by treating a queued entry as if it were already posted (which would satisfy the letter of "offline workflows" while quietly breaking the reconciliation guarantee for anyone who happened to look at the dashboard during the gap). The resolution was to make the *gap itself* visible and honest: a queued entry is visibly, distinctly "not yet posted" everywhere it could otherwise be mistaken for posted — the dashboard, the ledger, the aggregate totals — until the server actually confirms it.

**Why conflicts escalate to a server-side, school-wide table rather than staying client-side**: a stuck conflict that's only visible on the one device that queued it becomes invisible the moment that device is lost, switched, or simply not the one an available admin has in hand. Every other admin-facing concern in this system that matters across the whole school (anomalies, defaulter risk) is already school-scoped, not device-scoped — treating sync conflicts differently would have been an inconsistency with no good reason behind it, just an oversight waiting to happen.

**Why iOS gets a first-class manual sync path, not just a documented limitation**: Background Sync API support on iOS Safari is unreliable, and iOS is already a committed PWA target from Phase 9. A "works reliably except on iOS" caveat buried in a known-gaps list would be a real risk given the demo device is unknown in advance — building the manual "Sync Now" path as a primary, not fallback, interaction closes this before it becomes a live-demo surprise.

**Scope boundary held on purpose**: UPI was deliberately excluded from offline entry, not overlooked. UPI's trust model is inherently server-confirmed (webhook-driven); there's no meaningful "offline UPI" to build without either fabricating a payment confirmation the system can't actually verify, or building a parallel trust model solely for this one channel. Cash and cheque already rely on the admin's word, recorded and audit-logged — offline entry doesn't change what's being trusted, only when the system finds out about it.

**Accepted, documented gap**: the local IndexedDB queue is unencrypted device-side storage. Judged disproportionate to add client-side encryption for a hackathon build holding minimal data (amount, student reference, channel, timestamp) already behind an authenticated session — documented in `security.md` alongside this project's other honestly-disclosed gaps rather than solved with machinery the actual risk doesn't justify.

**Also folded into this pass**: the full, official evaluation rubric (nine criteria — see `project_overview.md` Stakeholders) was previously only partially represented in this documentation set (four of nine criteria were cited). Corrected in the same pass as this feature, per the Phase 8 governing sync policy — cross-referencing the newly available source material surfaced this gap incidentally, not as a separate remediation effort.

## Phase 11 — Parent Login Redesign: Phone/Email OTP, Replacing Magic-Link Email

**The problem being solved**: magic-link email login has two real weaknesses for this specific audience — email-checking habits are less reliable than SMS for many parents in this demographic, and the originally-considered alternative (real WhatsApp delivery for reminders) was already ruled impractical due to the WhatsApp Business API approval barrier. The question was whether SMS could solve both the reach problem and the WhatsApp barrier at once.

**Alternatives considered and rejected, in order:**
1. **Static SMS password, admin-generated, sent once at account creation.** Rejected: a permanent credential sent over unencrypted SMS is a real security downgrade from magic-link email (SIM-swap interception risk, plus this project would now need password storage, hashing, and reset flows it previously avoided entirely by being passwordless).
2. **Real production SMS via a directly-integrated aggregator (Twilio, MSG91, etc.), assuming "SMS instead of WhatsApp" sidesteps all delivery barriers.** Rejected as the *sole* path after research showed this assumption was wrong: any commercial SMS to Indian numbers — transactional, OTP, or otherwise — requires DLT registration with TRAI regardless of which aggregator sends it. This isn't a soft best-practice; unregistered SMS is mechanically blocked at the telecom operator level. DLT registration requires a registered business entity (GST/PAN/incorporation documents a hackathon team typically doesn't have), a real one-time fee (~₹5,900+GST), and a 3–7 working day approval window — meaning "just use Twilio directly" would have quietly traded the WhatsApp Business barrier for a *harder* one, not an easier one, if treated as the production path.
3. **OTP via Supabase Auth's native phone provider, sandboxed for the demo, real integration underneath.** Adopted. This resolves both prior rejections at once: no password to manage or leak (OTP only, same passwordless principle the original design already valued), and no dependency on DLT actually being registered for the parts of the system a demo or judge will ever touch, because Supabase's built-in Test OTP mechanism skips real SMS sending entirely for a configured set of demo numbers — the architecture is genuinely Twilio-integrated (real credentials, real provider configuration, functional for any number outside the test set), but nothing the demo depends on requires DLT compliance existing yet.

**Why email stays, as a fallback rather than being dropped**: dropping email entirely in favor of phone-only would have reintroduced a single point of failure — exactly the kind of risk this system's own design philosophy (RLS as the real enforcement, non-blocking AI, honest sync-conflict states) consistently avoids elsewhere. A judge testing with an arbitrary phone number not in the Test OTP set would otherwise have no way in at all. Keeping email as a standing, visible option (not a hidden fallback-only path) costs nothing — Supabase's built-in email OTP requires no additional provider or credential — and closes that gap for free.

**Why `shouldCreateUser: false` gets called out in four separate documents (`business_rules.md`, `security.md`, `system_architecture.md`, `implementation_plan.md`) rather than stated once**: this is the one line most likely to be silently omitted by an agent unfamiliar with Supabase Auth's default OTP behavior, and the consequence of omitting it — silent self-registration — directly contradicts a principle this project has otherwise enforced consistently since the original design (`security.md`: "no self-registration... which is what makes a parent account meaningful"). The repetition is deliberate, not redundant documentation drift.

**What changed structurally**: `USER.phone` is now required for parent accounts (previously only `email` existed on this table at all); `USER.email` is now optional for parents specifically. `createParentAccount` is now an explicit, named action rather than an implied consequence of "an admin creates the `PARENT_LINK`" — the original design was correct that admin-provisioning was the right model, but had never actually specified the mechanics of that provisioning step until this phase.

## Phase 12 — Team Collaboration Structure (4-Member Split)

Distinct from every phase before it: no product, architecture, or session content changed here — this phase is purely about *who* builds *what*, and in what order, across a 4-person team. Recorded anyway, for the same reason Phase 8's governing sync policy exists: a plan that looks correct on a first read and turns out to have gaps is exactly the failure mode this log is meant to catch before it costs build time, not just design time.

**A proposed team-split plan claimed that after Sessions 1+2 (Member 1, sequential), Sessions 3, 4, 5, and 6 could all proceed fully in parallel with no mock data needed anywhere.** That claim was checked directly against this project's actual cross-session dependencies (`implementation_plan.md`), not accepted at face value, and it was wrong in three specific, verifiable places:

1. **Session 6 is an integration phase, not parallel work.** It wraps Session 4's `processOcrUpload`/`answerDashboardQuery` with rate limiting and requires a fully working system for the demo rehearsal — it needs Sessions 3, 4, *and* 5 all merged, not just whichever session the same team member happened to finish right before it.
2. **Two specific Session 5 features have real dependencies beyond Session 1+2**: the Parent Copilot extends Session 4's `copilotQuery` function rather than being a new one, and the parent push toggle extends Session 3's push infrastructure. The original ownership table ("Member 2 owns Copilot") was corrected to reflect that Copilot is a genuinely shared function — Member 2 builds it with the Admin whitelist, Member 4 later extends the same function with the Parent whitelist.
3. **A handful of "touch another session's files" moments are real and necessary** (push triggers wired into Session 2 code, `copilotQuery` extended across two sessions, rate limiting wrapping Session 4 functions) but weren't reconciled against the plan's own "don't modify modules owned by others" rule. `AI_INSTRUCTIONS.md` Section 5 now names these explicitly as sanctioned exceptions, so an agent doesn't either avoid a necessary change out of caution or make an unlisted one without flagging it.

**What changed as a result**: `README.md` gained a full team-collaboration section (Project Structure, Development Workflow, Team Distribution, a three-phase Development Order instead of a two-phase one, Git Workflow with six session-scoped branches instead of four person-scoped ones, Merge Conflict Strategy, corrected Feature Ownership, Best Practices). A new `docs/AI_INSTRUCTIONS.md` was created as the master per-agent operating contract, referenced as the first thing any coding agent reads, ahead of the session-specific specification documents. The four Phase 8/9/10/11 companion documents (`AUDIT_REMEDIATION_PLAN.md` and the three `PHASE_*.md` files) were removed from `docs/` at the same time, per direct request — their content isn't lost, since every finding and rationale they contained already lives permanently in the relevant specification document's "added Phase N" annotations and in this log; the companion files were a convenience layer, not the only copy of that information.

## Phase 15 — Student Lifecycle & Exit Handling, Email Reminder Escalation, Client State Management

Two findings raised directly ahead of the build starting, both treated with the same rigor as a self-initiated audit finding — recorded here per this log's own standing practice (Phase 8's governing policy) of re-reading and editing every affected document's body text, not just noting the decision.

**1. No student exit/withdrawal concept, and a defaulter view that would silently fill with stale entries.** Phase 14 added `STUDENT.is_active` for roster deactivation generally, but did not address the specific case this raises: a student who withdraws, graduates, or transfers mid-year with an outstanding balance had no way to be removed from the risk-segmented Defaulter Tracking view — this project's own named differentiator — while still preserving their financial history and giving the admin an explicit choice about the outstanding balance (write off vs. carry forward), rather than either silently erasing debt or leaving a departed family on an active collections list indefinitely.

**Fix**: `STUDENT.is_active` (Phase 14) is superseded by `STUDENT.status` (`active` \| `withdrawn` \| `graduated` \| `transferred`) — a boolean couldn't express *why* a student left, which matters for both the admin's own record-keeping and for deciding what happens to any remaining balance. `updateStudentStatus` requires an explicit `balanceDisposition` (`write_off` \| `carry_forward`) whenever an outstanding balance exists at the time of the status change — `write_off` reuses the existing `applyWaiver` mechanism (no new financial mechanism invented), `carry_forward` leaves the balance collectible but the student is removed from the active Defaulter Tracking view either way, since that view exists to prioritize *actionable, current* risk, not to be a permanent list of every fee ever owed. `computeDefaulterScore` and the daily reminder-trigger job both now filter on `STUDENT.status = 'active'`. Historical `DEFAULTER_SCORE`/`FEE_ASSIGNMENT`/`TRANSACTION` data is never deleted — same non-negotiable pattern as every other soft-delete in this system — and remains fully visible on the Student Profile screen (Phase 14) regardless of status.

**2. Push notifications structurally under-reach the actual defaulter population.** Raised directly, and verified against this document set's own existing statements rather than taken at face value: push requires the parent to have installed the PWA and explicitly opted in (`ui_ux_specification.md` Global Requirements, Push Notification opt-in) — and a parent that disengaged enough to be behind on fees is, on average, less likely to have done either of those things than an engaged parent. The reminder system's actual job — reaching the parents least likely to already be checking a dashboard — was structurally weakest exactly where it mattered most.

**Research conducted**: transactional email (as distinct from WhatsApp/SMS) carries none of the barriers this project has already documented as blocking real WhatsApp/SMS delivery — no DLT registration, no WhatsApp Business API approval, no per-message regulatory cost (see `business_rules.md` Parent Account & Login Strategy, `security.md` Known Gaps). Reviewed current transactional email providers for a Next.js/Vercel stack at hackathon-then-early-production scale; **Resend** was selected — free tier (3,000 emails/month, 100/day) comfortably covers a single school's defaulter-reminder volume, first-party Next.js/TypeScript SDK support, and no credit card required to start. Postmark was considered as a more established alternative with a longer deliverability track record, noted as a reasonable upgrade path if real-world bounce/complaint volume ever demands it — not adopted now, since nothing about this build's scale requires it yet.

**This required revising Governing Principle 3**, not working around it — a real email API call is exactly what that principle's literal text prohibited. The revision is narrow and preserves the principle's actual point: **no reminder is ever delivered without an explicit, logged, human "mark sent" action — that part is unchanged and unweakened.** What changes is that for the email channel only, the existing `markReminderSent` action's admin-triggered "sent" transition now also dispatches one real, non-blocking message via Resend, using the exact drafted text already reviewable before that action is taken. WhatsApp/SMS remain simulated-only, exactly as before — this is not a general loosening of Principle 3, it is a third narrow, named exception of the same kind already carved out twice before (Push, Phase 9; OTP login, Phase 11), added for the same reason those were: a real, structural gap in this system's actual ability to reach the people it claims to serve. `project_overview.md` Governing Principle 3, `business_rules.md` Reminder Strategy, and `product_requirements.md` FR-16 are all corrected to state this consistently — per Phase 8's own rule, a decision recorded here is not evidence it was applied to the body text, so all three were directly re-read and edited.

**Also fixed in passing**: `api_specification.md` never actually listed a `markReminderSent` action — the Reminders Queue UI's "mark sent" button had no backing server action documented, the same class of gap `getRemindersQueue` closed in Phase 8. Added here since it's the exact function this phase's email dispatch attaches to.

**3. No mandated client-side state-management pattern for financial data.** Raised directly. Every screen showing financial data was previously specified only at the level of "must bind to a live query, never mock data" (`ui_ux_specification.md` Global Requirements) — sufficient for *what* data renders, but silent on *how* loading/stale/conflict states are represented, leaving each screen free to invent its own ad hoc handling. Given this system already has two states that must never be conflated with "showing current data" — a dropped Realtime connection (Global Requirements) and a queued-but-unsynced offline entry (Governing Principle 5) — an unstructured per-component approach is a real risk of one of those two states silently reading as "synced" somewhere.

**Fix**: TanStack Query (React Query) v5 added to the stack, wrapping every Supabase Realtime subscription and every server action call. Every screen rendering financial data must derive its render state from a five-value union — `idle -> loading -> synced | stale | conflict` — specified in full in `system_architecture.md` Client State Management (new section). `stale` and `conflict` are not new concepts invented by this phase; they formalize two states this document set already required (the Realtime-drop indicator, the offline sync-conflict state) into one consistent, mandatory rendering contract instead of leaving each screen to reconstruct the same idea independently. No new business logic changes as a result — this is a client-architecture requirement, not a change to what any number means.

## Considered, Not Built (Phase 8 additions — dispositioned, not silently dropped)

- **AI-assisted waiver/discount-amount suggestion** — considered, explicitly deferred. Same reasoning as the existing ML-risk-scoring exclusion (§10.1's rule-based-sufficiency finding): a waiver amount is a judgment call an admin should make deliberately, not one the system should pre-fill, given the audit-trail-native design philosophy applied everywhere else in this project.

- **"N new transactions since you last looked" live-update indicator on the dashboard** — considered, low-cost and directly reinforces the product's core "zero lag" claim in a way a judge/reviewer would notice immediately. Recommended as Session 3 polish-time work *if* the schedule allows, not made a hard requirement given the 6-day window.
