# Testing Strategy — Smart School FinTech Platform

## Purpose

Addresses a gap surfaced during Phase 8 design-audit remediation: no document in the original 13-document set specified any test strategy, despite the system's core claim being financial correctness. The per-session "Checkpoint before proceeding" steps in `implementation_plan.md` are manual, one-time demo verifications — they prove a feature works once, not that it keeps working as later sessions touch shared code. This document exists to close that gap without over-scoping a hackathon build: it targets automated coverage specifically at the logic where a silent regression is both easy to introduce and expensive to miss, not at exhaustive coverage of the whole system.

## Scope

Test targets, by session, for the modules where correctness matters most: reconciliation matching, idempotency, defaulter risk scoring, GST calculation, RLS policy enforcement. Does not mandate a specific test runner beyond a recommendation (Vitest, since it's the natural fit for a TypeScript/Next.js monorepo and requires no additional config beyond what a Next.js 15 + Prisma stack already has). Does not mandate UI/component testing or end-to-end browser testing — those remain manual per the existing checkpoint process, which is an acceptable scope boundary for a 6-day build.

## Why These Modules Specifically

Every test target below maps to a specific implementation trap that another document in this set already called out by name as easy to get wrong:

- `financial_engine.md` §4 explicitly names the off-by-one trap in reconciliation matching ("including the current transaction in its own expected-amount baseline would make every payment appear anomalous").
- `financial_engine.md` §1 (Phase 8 addition) names the concurrent-payment overpayment race.
- `business_rules.md` §Waiver Handling and the Phase 6 fix log name the waiver-triggers-recompute gap as something that was *actually missed* once already in this project's own history.
- `security.md` states RLS, not application code, is the real enforcement mechanism — which means RLS is exactly the kind of thing that looks correct in a manual click-through and can still be silently wrong for a query shape nobody happened to try by hand.
- **`system_architecture.md` AI Copilot Architecture (Phase 9) names the whitelist itself as the security boundary** — which means a test suite that only exercises example conversations, and never asserts against the whitelist definition directly, could pass indefinitely while a future edit quietly adds a write action to the list. This is the same category of risk as the RLS point above: correct-looking in normal use, silently wrong for a case nobody happened to try.

If a class of bug was important enough for another document to call out by name as a trap, it's important enough to have a regression test, not just a careful first implementation.

## Test Targets by Session

### Session 1 — Ledger Core
- `applyWaiver` / `applyPenalty` always produce a matching `AUDIT_LOG` row — assert directly against the DB after each call, not just against the function's return value.
- `WAIVER.reason` / `approved_by` and `PENALTY.reason` reject `null`/empty at both the application layer and (separately) confirm the DB constraint rejects a direct insert that bypasses the application layer entirely — two tests, not one, since the schema-level constraint is the actual backstop per `database_design.md`.
- `TRANSACTION.amount` `CHECK (amount > 0)` — confirm a direct insert attempt of `0` or a negative amount fails at the DB level.
- **`bulkImportStudents` partial-batch failure (added Phase 14)**: import a CSV with one valid row and one row missing a required field, assert the valid row creates a `STUDENT` and the invalid row is reported individually — never a total-batch rejection.
- **`bulkImportStudents` idempotent re-run (added Phase 14)**: import the same CSV twice, assert the second run creates zero new `STUDENT` rows for admission numbers already present (matched and skipped, not duplicated) — this is what makes the action safe to retry after a crash.
- **`createStudent` school-scoping (added Phase 14)**: assert `admission_number` uniqueness is enforced per `school_id`, not globally — two different schools may each have a student with the same admission number.
- **Deactivation preserves history (added Phase 14, revised Phase 15)**: create a student, assign a fee, record a payment, then call `updateStudentStatus` with `status: withdrawn`, `balanceDisposition: carry_forward` — assert the existing `FEE_ASSIGNMENT`/`TRANSACTION` rows are untouched and still return correctly from a query, same pattern as the existing `FEE_TYPE` deactivation test.
- **`updateStudentStatus` rejects missing disposition (added Phase 15)**: for a student with a nonzero remaining balance, call `updateStudentStatus` with a non-`active` status and no `balanceDisposition` — assert the call is rejected outright, not defaulted to either behavior.
- **`updateStudentStatus` write-off creates a real waiver (added Phase 15)**: call with `balanceDisposition: write_off`, assert a `WAIVER` row was created for the full remaining balance and a matching `AUDIT_LOG` row exists — same DB-level assertion discipline as the waiver/penalty test above, not just checking the function's return value.
- **`updateStudentStatus` on a zero-balance student (added Phase 15)**: assert the call succeeds with no `balanceDisposition` supplied and no `balanceDisposition` value is required or accepted when there's nothing to dispose of.

### Session 2 — Reconciliation
- **The off-by-one test, specifically**: post two sequential partial payments against the same `FEE_ASSIGNMENT` and assert the second payment's `expected_amount` in its `ANOMALY_FLAG` (if any) reflects the balance *before* that second payment, not including it.
- A payment matching the true remaining balance after a prior partial payment does **not** trigger `flagged` — this is the "legitimate partial payment is not an anomaly" case from `financial_engine.md` §4, worth its own explicit test since it's the easy case to accidentally break while fixing the off-by-one case above.
- UPI webhook idempotency: fire the same `ref_number` twice, assert exactly one `TRANSACTION` row exists and the second call returns the existing record.
- **Concurrent payment lock**: two simulated-concurrent `recordPayment` calls against the same `FEE_ASSIGNMENT` for amounts that would together overpay it — assert the second call, after the first commits, sees the updated balance and is correctly rejected (or correctly permitted if it still fits), never that both succeed and jointly overpay.
- `markChequeBounced` reopens the balance (via exclusion from the `amount_paid` sum, per `financial_engine.md` §3) and triggers `computeDefaulterScore` — assert both in one test, since this is the exact cross-engine dependency `user_flows.md` names as the one most likely to be implemented correctly in isolation while missing the interaction.
- **Offline queue write (added Phase 10)**: with `navigator.onLine` mocked false, submit a cash entry and assert it writes to IndexedDB with a `local_id`, `queued` state, and makes zero network calls — a queue write that silently also attempts (and fails) a network request is a bug this test exists to catch, not just "did the data get saved."
- **Offline queue rejects UPI (added Phase 10)**: assert the offline write path throws/rejects if `channel: upi` is passed — this boundary (`business_rules.md` Offline Payment Entry Strategy) should be enforced in code, not just by the UI never offering the option.

### Session 3 — Dashboard / Defaulter Scoring, PWA + Admin Push *(scope extended Phase 9)*
- `computeDefaulterScore` formula: at least one test per weight (days-overdue, broken-promise, remaining-balance-ratio) confirming each contributes independently and the thresholds (60/30) classify correctly at and around the boundary values.
- `broken_promise_count` query (see `business_rules.md`, Phase 8 addition): confirm it only counts reminders where the assignment is *currently* unpaid past due date, not reminders sent on assignments later cleared.
- A partially-paid student scores strictly lower than an otherwise-identical student who has paid nothing — this is stated as "a deliberate design requirement, not an incidental side effect" in `business_rules.md`, which makes it worth a direct comparative test rather than trusting the formula's shape.
- **`sendPushNotification` non-blocking guarantee (added Phase 9)**: simulate a push send failure (invalid/expired subscription) and assert the triggering write (`recordPayment`, `markChequeBounced`, anomaly flag creation) already committed and returned successfully regardless — same ordering-guarantee test pattern as the Gemini narration tests below, applied to a different async side effect.
- **`PUSH_SUBSCRIPTION` cleanup**: simulate a 404/410 response from a push send and assert the corresponding row is deleted, not retried indefinitely.
- **`PUSH_SUBSCRIPTION` RLS**: authenticate as User A, attempt a direct query against User B's subscription rows, assert zero rows returned — same pattern as every other user-linked table's RLS test.
- **Offline sync happy path (added Phase 10)**: queue an offline cash entry (Session 2 test above), simulate reconnection, assert `syncOfflinePayment` fires, the entry posts through the real `recordPayment` path, and the local queue entry is removed only after server confirmation — never removed optimistically before the server call resolves.
- **Offline sync idempotency**: simulate the same `local_id` syncing twice (e.g., a retried Background Sync attempt) and assert only one `TRANSACTION` posts — same idempotency discipline as the UPI webhook test, applied to a different trigger.
- **Offline sync conflict — arguably the most important test added in this pass**: queue an offline entry, then independently change the target `FEE_ASSIGNMENT`'s balance (simulating a payment made elsewhere while offline) such that the queued entry would now overpay, then simulate reconnection. Assert three things together, not separately: (1) `recordPayment` correctly rejects it, (2) an `OFFLINE_SYNC_CONFLICT` row is created, visible via `getSyncConflicts` to a *different* admin session at the same school, and (3) the amount is never posted, partially posted, or silently adjusted. A test that only checks one of these three could pass while the other two silently regress.
- **`getSyncConflicts` RLS**: confirm it's school-scoped (any admin at the school sees it) but not cross-school — same pattern as every other admin-facing table, explicitly re-verified here because this table is deliberately *not* user-scoped like most others in this system, making it the one place a copy-pasted RLS policy from a user-scoped table would be silently wrong.
- **`getStudentProfile` consistency (added Phase 14)**: for a student with fee assignments, transactions across multiple channels, a waiver, and a reminder, assert every figure the aggregation returns matches an independent direct query against the same underlying tables — this action must never compute or transform a number differently than the tables it reads from already state.
- **`getStudentProfile` school-scoping (added Phase 14)**: as an Admin at School A, attempt `getStudentProfile` against a School B student's ID, assert it returns nothing — same RLS-inheritance pattern as every other admin action.
- **`computeDefaulterScore` status exclusion (added Phase 15)**: create a high-risk-scoring student, set their status to `withdrawn`, assert they no longer appear in the active Defaulter Tracking view on the next computation — then assert their historical `DEFAULTER_SCORE` rows are still returned intact by `getStudentProfile`, since exclusion from the active view must not mean the history was deleted.
- **Five-state union rendering (added Phase 15)**: for the Dashboard and Student Profile screens, assert each of `loading`, `synced`, `stale` (simulate a dropped Realtime connection), and `conflict` (an unresolved `OFFLINE_SYNC_CONFLICT` for the displayed student/range) renders a visually distinct state — specifically assert `conflict` never shares the same treatment as `synced`, since Governing Principle 5 makes this the one confusion this pattern exists to prevent.

### Session 4 — AI Layer, Admin Copilot, Weekly Digest *(scope extended Phase 9)*
- `narrateAnomaly` / `narrateDefaulterInsight` failure simulation: force a Gemini call to fail or time out and assert the payment-critical write it relates to already succeeded and returned before the narration call ran — this is testing an ordering guarantee, not the AI output itself.
- `confirmOcrEntry` is the only path that can set `OCR_STAGING.confirmed = true` — assert no other code path can flip it, and assert `processOcrUpload` alone never causes a `TRANSACTION` to be created.
- **Copilot whitelist assertion (added Phase 9 — arguably the single most important test added in this pass)**: assert directly against the `copilotQuery` Admin whitelist array/config that it does not contain `recordPayment`, `applyWaiver`, `applyPenalty`, `markChequeBounced`, or `reconcileMissedUpiPayment` — a static assertion on the whitelist definition itself, not just a behavioral test of one conversation. A behavioral test can pass by accident if the test's specific prompts never happen to trigger the write path; a static whitelist assertion cannot.
- **Copilot cross-tenant test**: as an Admin at School A, ask the Copilot a question requiring School B's data; assert it cannot answer, and assert this is because the underlying whitelisted action itself returned nothing (RLS-scoped), not because of a prompt-level refusal that a differently-worded question might bypass.
- `generateWeeklyDigest`: assert its trend figures match independently-computed values from `financial_engine.md`'s existing derivation formulas for the same date range — the digest must narrate real computed numbers, never numbers Gemini produces itself.

### Session 5 — Parent Portal / RLS, Parent Push + Parent Copilot, Parent OTP Login *(scope extended Phase 9, redesigned Phase 11)*
- **The single highest-value test in this entire suite**: authenticate as Parent A, attempt a direct query (not through an application action) against Parent B's linked student's `FEE_ASSIGNMENT`/`TRANSACTION`/`RECEIPT` rows, assert zero rows returned. Repeat for every table in the Parent RLS policy table in `security.md`, including the "no access at all" tables (`WAIVER`, `PENALTY`, `AUDIT_LOG`, `ANOMALY_FLAG`, `OCR_STAGING`, `REMINDER_LOG`, `DEFAULTER_SCORE`) — assert a parent role querying any of these directly gets zero rows, not an error that might be caught and hidden by the application layer instead.
- `payDueViaUpi` channel-locking: assert a parent cannot pass `channel: cash` or `channel: cheque` through the parent-facing action even if the underlying `recordPayment` signature technically accepts it.
- This suite should be kept in the permanent regression set for the life of the project, not just run once at Session 5 — any future schema or RLS policy change must re-run it before merging.
- **Parent Copilot whitelist assertion (added Phase 9)**: same static-assertion pattern as the Admin Copilot test above, applied to the Parent whitelist — additionally assert `risk_level`/`DEFAULTER_SCORE`/`WAIVER`/`AUDIT_LOG` never appear in any tool the Parent whitelist can call, not just that write actions are absent.
- **GST explainer grounding test**: ask the Parent Copilot to explain GST on a specific fee, assert the response's tax rate/treatment matches the `FEE_TYPE.gst_treatment`/`gst_rate` actually stored for that fee — catches a Copilot that answers plausibly but incorrectly from general knowledge instead of the specific stored configuration.
- **`createParentAccount` transactional integrity (added Phase 11)**: assert a call with zero `studentIds` is rejected outright — a parent account with no linked student must never be creatable, per `business_rules.md` Parent Account & Login Strategy. Assert a partial failure (e.g., `USER` row created but a `PARENT_LINK` insert fails) leaves no orphaned `USER` row — the whole operation must be one transaction, not a sequence of independently-committing writes.
- **The single most important test added in this session, arguably in this entire suite**: attempt `signInWithOtp` (both phone and email channels, tested separately) against a phone/email with no corresponding `USER` row, and assert (1) the call fails, (2) no new `auth.users`/`USER` row is created as a side effect of the attempt, and (3) a subsequent legitimate `createParentAccount` call for that same phone/email still succeeds cleanly afterward — a test that only checks "the call returned an error" without also checking "no account was silently created anyway" could pass while `shouldCreateUser` defaults back to `true` in a future edit and nobody notices.
- **Duplicate-phone rejection**: attempt `createParentAccount` with a phone number that already exists on another `USER` row, assert it fails with a distinguishable error (not a generic 500) that a UI could reasonably turn into the "already registered, link this student instead" message specified in `ui_ux_specification.md`.

### Session 6 — GST / Receipts
- GST-inclusive calculation: for a known `gst_rate` and `TRANSACTION.amount`, assert `gst_amount` matches the back-calculated value exactly (`amount × rate/(100+rate)`), and assert there is no code path producing the exclusive-formula result — this test exists specifically to prevent C-1 (the resolved-but-previously-contradictory GST convention) from silently regressing.
- `RECEIPT.gst_details` snapshot: change a `FEE_TYPE`'s `gst_rate` after a receipt already exists, assert the existing receipt's stored `gst_details` is unchanged.
- Rate limiting: assert a burst of rapid calls to `processOcrUpload`/`answerDashboardQuery` from the same admin session is rejected past the configured threshold, and a normal single-call pattern is never falsely limited. **Added Phase 14**: extend this same test to `generateReconciliationReport`.
- **`generateReconciliationReport` figure parity (added Phase 14)**: for a known date range with test data, assert every figure in the generated report (collected by channel, outstanding, waived, class-wise breakdown) matches `getLedgerSnapshot`'s output for the identical range exactly — the report must never introduce a second, potentially divergent calculation path.
- **`generateReconciliationReport` audit logging (added Phase 14)**: assert every successful call produces an `AUDIT_LOG` row with `action: report_exported`, the correct actor, and the correct date range — same assert-directly-against-the-DB pattern as the Session 1 waiver/penalty audit test.
- **`markReminderSent` non-blocking guarantee (added Phase 15)**: simulate a slow/failed Resend call and assert `REMINDER_LOG.status` still updates and the admin's action still completes without hanging — same ordering-guarantee pattern as the Session 3 push notification test, applied to the third async side-effect channel in this system.
- **`markReminderSent` on a parent with no email (added Phase 15)**: assert the call succeeds as a no-op dispatch and the row is distinguishable from both `sent` and `failed` — the UI's "no email on file" state (`ui_ux_specification.md`) depends on this being a distinct outcome, not folded into `failed`.
- **`markReminderSent` real dispatch, whatsapp/sms untouched (added Phase 15)**: assert calling this action on a `whatsapp`/`sms` row still only flips `status` to `simulated_sent` with zero external calls made — this is the test that would catch an implementation accidentally routing every channel through the new Resend code path instead of just `email`.

## What This Document Deliberately Does Not Cover

- UI/component/visual testing — remains manual per the existing per-session checkpoint process; not a correctness-critical path in the same sense as the modules above.
- End-to-end browser automation — reasonable for a future extension, not required for this build window.
- Load/performance testing — out of scope per `system_architecture.md`'s own scalability framing (real-scale concerns are explicitly deferred there; this document stays consistent with that boundary rather than introducing a new one).

## Assumptions

- Tests run against a local or ephemeral test database, never against the single `production` environment referenced in `system_architecture.md` — this is a direct consequence of that document's Phase 8 environment-separation correction (see `decision_log.md` Phase 8), not a new requirement invented here.
- Vitest is a recommendation, not a hard requirement — any TypeScript-native test runner the agent is already comfortable with satisfies this document's intent.
