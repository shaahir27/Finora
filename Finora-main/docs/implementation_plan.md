# Implementation Plan — Smart School FinTech Platform

## Purpose

A build-sequence guide for AI coding agents, written as a series of self-contained session briefs. Each day/session has an explicit scope boundary, deliverable, exclusions, and a checkpoint to hand off to the next session — matching a PROGRESS.md-style handoff pattern rather than a single monolithic build instruction.

## Scope

Build ordering and session-level checkpoints only. Full technical detail for each deliverable lives in the documents referenced per session; this document sequences them, it does not restate them.

## Testing (added Phase 8)

See `testing_strategy.md` for full detail. Summary: the manual "Checkpoint before proceeding" step below each session proves a feature works *once*; it does not protect against a later session silently breaking it. From Session 1 onward, each session's checkpoint is not considered complete until the automated tests specified for that session's modules in `testing_strategy.md` also pass — not as a separate later pass, but as part of that session's own definition of done.

## Build Logging *(added alongside build_history/ setup)*

See `BUILD_LOGGING_PROTOCOL.md` for full detail. Summary: every feature built in a session gets a log in `build_history/session_XX_.../feature_[name].md`, using `templates/log_schema.md`. Same enforcement pattern as Testing above — a session's checkpoint is not complete until every feature it built is logged and `build_history/index.md` reflects it, not as cleanup work after the fact.

## Session 1 — Ledger Core (Fee Engine + Ledger Engine, No UI Polish)

**Build**: `SCHOOL`, `USER`, `STUDENT`, `FEE_TYPE`, `FEE_ASSIGNMENT`, `TRANSACTION`, `WAIVER`, `PENALTY`, `AUDIT_LOG` tables per `database_design.md`. Server actions: `createFeeType`, `assignFee`, `recordPayment`, `reverseTransaction`, `applyWaiver`, `applyPenalty` per `api_specification.md`. **Added Phase 14, same session, since everything else in this list has a hard dependency on it**: `createStudent`, `bulkImportStudents`, `updateStudent` per `api_specification.md` Student Directory — build these *first* within the session, since `assignFee` and every downstream action assume a `STUDENT` row already exists. **Added Phase 15, same session, since it's a thin action over the same `STUDENT`/`WAIVER` tables already being built here**: `updateStudentStatus` (`STUDENT.status`, `status_changed_at`, `balance_disposition` fields per `database_design.md`) — its `write_off` path calls `applyWaiver`, built earlier in this same list, so no forward reference to a later session is introduced.

**Exclusions**: no Razorpay integration yet — `recordPayment` for `channel: upi` accepts a manually-passed amount/ref for now, same code path Razorpay will call in Session 2. No dashboard. No auth roles beyond a single hardcoded admin for testing. No Student Directory UI yet (see Session 3) — these actions exist and are testable this session, but the roster screen itself is a Session 3 concern alongside the rest of the real-data UI.

**Checkpoint before proceeding**: confirm every waiver/penalty write also produces an `AUDIT_LOG` row (see `business_rules.md` §3) — this is the single hardest thing to retrofit later if missed now. Automated tests for this session per `testing_strategy.md` §Session 1 must also pass, including the concurrent-payment lock test (`financial_engine.md` §1 Concurrency). **Added Phase 14**: run `bulkImportStudents` against a CSV with at least one deliberately malformed row and confirm the valid rows still import while the bad row is reported individually, not silently discarded or aborting the whole batch. **Added Phase 15**: confirm `updateStudentStatus` actually rejects a call that omits `balanceDisposition` while a nonzero balance exists — this is the one behavior in this session most likely to be implemented as a silent default instead of a hard rejection if not checked explicitly.

## Session 2 — Razorpay Sandbox + Reconciliation State Machine

**Build**: `initiateUpiSandboxPayment`, `handleRazorpayWebhook` (with idempotency check on `ref_number` per `system_architecture.md`), wired into Session 1's `recordPayment`. `reconciliation_status` enum on `TRANSACTION` including `cheque_pending`. `detectAnomaly` pure function in `packages/rules` (zero external calls, per the package isolation requirement in `system_architecture.md`). Cheque-specific actions: `markChequeCleared`, `markChequeBounced` (must trigger `computeDefaulterScore` recompute per `financial_engine.md` §3). **Added Phase 10, same session** since it extends the cash/cheque entry form built here: the IndexedDB offline-write path — client-generated `local_id`, queue write when `navigator.onLine` is false — per `business_rules.md` Offline Payment Entry Strategy. The *sync* side (Background Sync registration, manual Sync Now, conflict UI) waits for Session 3's service worker; this session only needs to make the entry form capable of queueing locally instead of failing outright when offline.

**Exclusions**: no anomaly narration (Gemini) yet — just the boolean flag and reason string. No offline sync execution yet (see Session 3) — a queued entry sits locally, unsynced, until then; that's expected, not a bug to chase down within this session.

**Checkpoint before proceeding**: manually trigger one cash, one UPI sandbox, and one cheque entry and confirm all three post to the same ledger view with correct `reconciliation_status`. This is the literal reconciliation demo moment (§13.1 of the research) — if it doesn't work cleanly here, everything downstream is at risk, and the next session should absorb the fix before adding anything new. Automated tests per `testing_strategy.md` §Session 2 must also pass, including the reconciliation off-by-one regression test (`financial_engine.md` §4) and webhook idempotency. **Added Phase 10**: with the browser's network throttled to offline, submit a cash entry and confirm it writes to IndexedDB with a `queued` state and does *not* attempt (or fail attempting) a network call — the absence of an error here is the actual pass condition, not a success message.

## Session 3 — Glassmorphism Admin Dashboard, Wired to Real Data, PWA + Admin Push, Offline Sync *(scope extended Phase 9, Phase 10, Phase 15)*

**Build**: **Added Phase 15, first thing built in this session, since every other deliverable below renders through it**: TanStack Query v5 setup wrapping Supabase Realtime subscriptions and server action calls, and the shared five-state (`idle`/`loading`/`synced`/`stale`/`conflict`) rendering contract per `system_architecture.md` Client State Management — every screen built in this session (and every screen built in Sessions 4–6) renders through this from the start, not retrofitted after the fact. Dashboard reading live from `getLedgerSnapshot`, Supabase Realtime subscription — no polling, no mock numbers. `computeDefaulterScore` rule engine function plus `DEFAULTER_SCORE` table and defaulter view sorted by `risk_level`, **filtered to `STUDENT.status = 'active'` (added Phase 15 — see `business_rules.md` Defaulter Risk Segmentation)**. Visual treatment per `design_system.md`, including its final color values (Forest Ledger, Option A — locked; do not build against placeholder tokens or wait for a separate palette handoff). **Added Phase 9, same session** since it's the first real UI pass: PWA setup (`manifest.json`, service worker, iOS install banner per `ui_ux_specification.md` Global Requirements — see `system_architecture.md` PWA & Push Notifications for the offline-banner behavior), the `PUSH_SUBSCRIPTION` table plus `subscribeToPush`/`unsubscribeFromPush`/`sendPushNotification` actions, the admin-side push settings toggle, and wiring admin push triggers (payment posted, cheque bounced, anomaly flagged) into this and Session 2's existing code per `business_rules.md` Push Notification Strategy. **Added Phase 10, same session** since it depends on this session's own service worker: Background Sync registration against Session 2's local queue, `syncOfflinePayment`/`reportSyncConflict`/`getSyncConflicts`/`resolveSyncConflict`, the Offline Sync Queue screen and its persistent pending-count badge, the manual "Sync Now" action (primary path on iOS), and wiring conflict escalation into this session's push notification triggers. **Added Phase 14, same session, since it shares this session's data layer and visual treatment**: the ADMIN — Student Directory (Roster) screen (wired to Session 1's `createStudent`/`bulkImportStudents`/`updateStudent`) and the ADMIN — Student Profile screen (wired to the new `getStudentProfile` action) per `ui_ux_specification.md`. **Added Phase 15, same session, since it's a control on the Student Directory/Profile screens just built above**: the "Change Status" action wired to Session 1's `updateStudentStatus`, including the submit-blocking `balanceDisposition` prompt.

**Exclusions**: no AI narration on the dashboard yet — defaulter view shows `risk_level` and `computed_reason` as plain text only. **Phase 14 addition**: `getStudentProfile` is a pure read aggregation over data this session (and Sessions 1–2) already compute — it introduces no new business logic of its own. **Phase 15 addition**: TanStack Query setup here is a client-architecture change only — it does not alter what any query returns or what any number means, only how its loading/stale/conflict state is represented.

**Checkpoint before proceeding**: confirm the dashboard updates in real time when a transaction is recorded from a separate browser tab/session — proves Realtime wiring, not just correct initial page load. **Added Phase 9**: confirm the app is installable (Chrome install icon appears; iOS shows the manual banner), confirm a test push notification actually arrives on a subscribed device when a payment is posted, and confirm an unsubscribed device receives nothing. Confirm offline mode shows the "last synced at" banner rather than stale-as-current data. **Added Phase 10**: take the queued offline entry from Session 2's checkpoint, restore connectivity, and confirm it syncs automatically (or via "Sync Now" if testing on iOS/an unsupported browser) and appears correctly in the ledger — then, separately, queue a second offline entry, deliberately change that student's balance from another session before reconnecting, and confirm the sync attempt produces a visible Sync Conflict rather than silently posting an incorrect amount or silently failing. **This second check matters more than the first** — the happy path is the easy 90% of this feature; the conflict path is the part that protects the reconciliation guarantee this whole product is built around. **Added Phase 14**: open a Student Profile for a student with existing fee assignments, payments, and a waiver from Sessions 1–2's test data, and confirm every figure shown matches what the Ledger and Defaulter views already show for that same student — this is testing that the aggregation reads correctly, not introducing a new number to verify independently. **Added Phase 15**: change a currently-at-risk test student's status to `withdrawn` with `carry_forward` chosen, and confirm they disappear from the Defaulter Tracking view on next load while their balance and history remain fully intact and visible on their Student Profile — then repeat with `write_off` chosen and confirm a `WAIVER` row was actually created for the full remaining balance, not just a UI-level hide.

## Session 4 — AI Layer (7 Features, updated Phase 9 — was 5), Admin Copilot, Weekly Digest

**Build**: `narrateDefaulterInsight`, `answerDashboardQuery`, `narrateAnomaly`, `draftReminderText`, `processOcrUpload`/`confirmOcrEntry` per exact contracts in `api_specification.md`. **Added Phase 9, same session**: `generateWeeklyDigest`, `copilotQuery` (Admin whitelist only — Parent whitelist waits for Session 5, since it depends on parent-facing actions that don't exist yet), `answerHowDoI`, and the Admin Copilot Tab UI per `ui_ux_specification.md`.

**Hard constraint to restate explicitly for this session**: Gemini calls only narrate, draft, or read — they never write to `TRANSACTION` directly. `confirmOcrEntry` is the only function permitted to post an OCR-originated payment, and only after explicit admin confirmation (see `user_flows.md` Workflow E). Narration calls (`narrateAnomaly`, `narrateDefaulterInsight`) must be asynchronous relative to the payment-critical path they relate to (see `system_architecture.md` integration contracts). **The same constraint applies to the Copilot, restated because it's the easiest place for an agent to accidentally reintroduce a write path**: `copilotQuery`'s whitelist must not include `recordPayment`, `applyWaiver`, `applyPenalty`, or `markChequeBounced` under any circumstance — verify the whitelist array directly, don't just test that the happy-path conversation looks right.

**Checkpoint before proceeding**: test the OCR flow specifically by uploading a deliberately wrong-amount receipt image and confirm the staged (unconfirmed) row does not affect any dashboard number until explicitly confirmed. **Added Phase 9**: open the Admin Copilot tab and confirm the weekly digest loads as the first message; ask it a question requiring cross-school data ("show me School B's collections" while logged in as a School A admin) and confirm it correctly cannot answer — this is testing that the whitelist's RLS inheritance actually holds, not just that the feature works for the happy path.

## Session 5 — Parent Portal + Hindi Toggle, Parent Push + Parent Copilot, Parent OTP Login *(scope extended Phase 9, redesigned Phase 11)*

**Build**: parent Auth role, RLS policies exactly per `security.md`, `getMyChildrenDues`/`payDueViaUpi`/`getMyPaymentHistory` per `api_specification.md`, including partial-payment support and the multi-child selector logic from `ui_ux_specification.md`. `next-intl` (or equivalent) on parent routes only. **Added Phase 9, same session**: parent-side push settings toggle + payment-confirmation trigger, and the Parent Copilot Tab (`copilotQuery` with the Parent whitelist, GST-explainer tool, `answerHowDoI` scoped to parent topics) per `ui_ux_specification.md`. **Redesigned Phase 11, replacing this session's original magic-link build**: Twilio configured as Supabase Auth's phone provider, Test OTP numbers configured for demo accounts, the phone-primary/email-fallback login screen, `createParentAccount`/`addStudentToParent`/`removeStudentFromParent` (admin-side, but built here since this is where parent-account logic lives), and the ADMIN — Add Parent screen per `ui_ux_specification.md`.

**Non-negotiable easy-to-miss detail, called out explicitly because it's a one-line omission with a real consequence**: every `signInWithOtp` call, both channels, must pass `shouldCreateUser: false`. Without it, an unrecognized phone/email silently gets a brand-new account instead of a clear "not registered" error — quietly reopening the no-self-registration principle this system otherwise enforces everywhere else (`business_rules.md` Parent Account & Login Strategy).

**This is the session most likely to get compressed if earlier checkpoints failed and ate buffer time.** If time is short, ship the core payment flow (login, view dues, pay) first and defer receipt download, the Hindi toggle, or the Phase 9 additions in that order — the RLS/schema work from earlier sessions makes this a safe place to cut, since nothing else in the system depends on the parent UI existing, and the Parent Copilot/push additions are themselves the lowest-priority items within this already-cuttable session. **The OTP login work itself is not cuttable** — it's how a parent gets in at all, unlike the Copilot/push additions layered on top of that access.

**Checkpoint before proceeding**: confirm, from a parent session, that a direct query attempt against another family's data is blocked at the RLS layer, not merely hidden by the UI — this is the actual proof point for the security claim in `security.md`. Automated RLS tests per `testing_strategy.md` §Session 5 must also pass and should be kept in the suite permanently — this is the single highest-value regression test in the entire system given how much of the security model rests on RLS alone. **Added Phase 9**: repeat the cross-tenant Copilot test from Session 4's checkpoint, this time as a parent attempting to ask about another family's dues — confirm it's blocked for the same structural reason (the whitelist's underlying actions are RLS-scoped), not a separate check. **Added Phase 11**: attempt an OTP request (either channel) against a phone/email that was never provisioned via `createParentAccount` and confirm it fails with the correct message rather than succeeding into a new account — this is the single most important check in this session's login work, more important than confirming a registered number's happy path, because a happy-path failure is obvious immediately and a silent self-registration hole might not be.

## Session 6 — Differentiators, Receipts, Reminders, Rate Limiting, Polish, Demo Rehearsal

**Build**: PDF receipt generation (A4 + thermal, with GST fields per `financial_engine.md` §5), `REMINDER_LOG` UI (logged/simulated-sent queue with the stale-reminder warning from `user_flows.md` Workflow D), EMI "Coming Soon" static stub, and **a simple per-admin-session rate limit on `processOcrUpload` and `answerDashboardQuery`** (moved into scope Phase 8 — previously an unassigned Future Extension despite being flagged as a gap in three separate documents; see `system_architecture.md`). **Added Phase 14, same session, as it's the same kind of polish-phase, non-blocking-to-earlier-sessions work**: `generateReconciliationReport` and the ADMIN — Reports & Export screen per `api_specification.md`/`ui_ux_specification.md`, plus extending this session's rate limit to cover it — a third admin-facing action calling out to generate a potentially large export is the same class of abuse/cost risk as the two Gemini-backed endpoints already in scope here. **Added Phase 15, same session, since it's a completion of the Reminders Queue UI already being built here**: Resend integration and `markReminderSent` per `api_specification.md`/`business_rules.md` Email Reminder Escalation, plus the `sent`/`failed`/"no email on file" states on the Reminders Queue screen per `ui_ux_specification.md`.

**Checkpoint before proceeding**: confirm the rate limit actually rejects a burst of rapid calls to both Gemini-backed endpoints in a quick manual test, and confirm a normal single-admin usage pattern is never falsely limited. **Added Phase 14**: generate a reconciliation report for a date range with known test data and confirm every figure matches `getLedgerSnapshot`'s dashboard output for the identical range exactly, then confirm the export produced an `AUDIT_LOG` row with the correct actor and date range. **Added Phase 15**: mark an `email`-channel test reminder sent for a parent with an email on file, confirm it actually arrives (check the Resend dashboard/inbox, not just the DB status flipping); then mark one sent for a parent with no email on file and confirm the UI shows "no email on file," not a silent no-op or a false success; then deliberately use an invalid address and confirm the row lands in `failed` with `dispatch_error` populated, not stuck in a permanent loading state.

**Reserve the final hours** for a full end-to-end rehearsal of the reconciliation demo script (cash + UPI + cheque → live ledger → parent pays → admin sees it instantly), run at least twice on the actual device/browser intended for presentation. The glassmorphism accessibility risk named in `design_system.md` (blur/contrast on lower-end devices) only surfaces in a real dry run, not in code review — **also spot-check rendered badge contrast specifically** (added Phase 8): the risk-medium/cheque-pending copper token was adjusted for a stronger contrast margin during design-audit remediation, which reduces but doesn't eliminate the value of confirming it reads correctly on the actual presentation display, especially under stage lighting or a projector.

**Gemini demo-day fallback rehearsal (added Phase 9)**: deliberately simulate a Gemini failure (temporarily set an invalid API key, or throttle the network to force a timeout) at least once during rehearsal for each of the now-seven AI features, and confirm every one degrades the way its spec says it should (rule-based fallback text for narration, a plain error state for `answerDashboardQuery`/Copilot rather than a stuck spinner) — this is verifying the non-blocking design actually holds under a real failure, not just reading correctly in the code. Have one specific, pre-confirmed "known good" Copilot exchange ready to fall back to narrating manually if live Gemini calls are unreliable on judging Wi-Fi — this doesn't need to be built into the app, just decided and rehearsed as a presenter fallback.

## Handoff Format

Each session above should be handed to an agent as its own scoped prompt, with a pointer back to the relevant specification document sections (rather than re-pasting full context each time) — this keeps agent context tight and matches an existing lean-handoff working pattern. Recommend a short PROGRESS.md-style note at the end of each session capturing: what was built, what checkpoint passed/failed, and what's explicitly deferred to the next session.

## Assumptions

- Sessions are sequential, one per working day, matching a roughly 6-day build window — but the plan is equally valid compressed or expanded, since each session's boundary is defined by scope, not a fixed duration.
- Later sessions assume earlier checkpoints passed; a failed checkpoint should be resolved before the next session begins, not carried forward silently.

## Future Extensions

Wiring the per-session test suite (now in-scope, see `testing_strategy.md`) into an automated CI pipeline that runs on every commit — the tests themselves are no longer deferred as of Phase 8, but CI automation of *when* they run is still a reasonable next step beyond the current manual-per-session-gate approach.
